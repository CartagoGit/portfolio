# DelendAI for this portfolio

The workspace runs the fixed local DelendAI 0.3.0 install through the `delendai-stable` launcher (`~/.local/bin/delendai-stable`, installed under `~/.local/share/delendai/stable`) while the package is unpublished. The server is `delendai` in `.vscode/mcp.json`; a future stable bump needs no edit here.

The selected plugins are deliberately narrow:

- `proposals` coordinates scoped pieces of portfolio work.
- `memory`, `git`, `search`, `quality` and `docs` help agents retain context and verify changes.
- `portfolio-content` is this workspace's local plugin. It audits public-content boundaries and lists image placeholders, without reading any external or employer workspace.

Run:

```bash
bun run mcp:check       # host boot + plugin surface
bun run mcp:test        # portfolio-content plugin unit tests
bun run mcp:typecheck   # portfolio-content plugin typecheck
bun run mcp:all         # all three of the above, gated
```

## Proposals folder

`docs/delendai/proposals/` follows the canonical delendai proposal
layout (the `proposal_adopt` tool mirrors it). Every proposal lives in a
status folder that matches its frontmatter `status`:

| Folder | Meaning |
|---|---|
| `ready/` | proposal reviewed, ready to start |
| `in-progress/` | currently being worked on |
| `review/` | awaiting peer review |
| `done/` | completed + verified |
| `paused/` | on hold |
| `blocked/` | waiting on a dependency |
| `retired/` | abandoned |

`index.json` is regenerated by `delendai_sync_proposals`; do not edit
it by hand.

## Local plugin layout (`portfolio-content`)

The portfolio host ships its own plugin — loadable by the delendai
core the same way first-party plugins are. It lives under
[`plugins/portfolio-content/`](../../plugins/portfolio-content/)
and mirrors the canonical layered shape (see
`plugins/deps/` in the DelendAI install for the reference):

```
plugins/portfolio-content/
├── README.md
├── package.json
├── tsconfig.json
├── vitest.config.ts
├── src/
│   ├── plugin.entrypoint.ts                 ← definePlugin(...) — loadable entry
│   ├── public/index.barrel.ts          ← barrel: re-exports engine + types
│   └── lib/
│       ├── contracts/interfaces/{audit,briefs}.interface.ts
│       ├── services/{audit,briefs}.ts     ← pure engine (DI via interfaces)
│       └── tools/{audit-tool,briefs-tool}.ts ← IToolRegistration builders
└── tests/
    ├── helpers/fake-context.helper.ts
    └── portfolio-content.spec.ts
```

Engine functions take injectable readers (`IPortfolioAuditReader`) so
the engine is side-effect-free. Tool builders return
`IToolRegistration[]` and use `toolJson` / `toolOk` / `toolError` from
`@delendai/core/public` for the contract envelope. Every tool
declares both `inputSchema` and `outputSchema`; tests instantiate a
fake `IMcpPluginContext` and capture the registered handlers so the
plugin can be exercised without spinning up a transport.

The legacy single-file variant of the plugin was rewritten in place;
the canonical path is `plugins/portfolio-content/src/plugin.entrypoint.ts`
and is registered in `delendai.config.json` via `path:`.
